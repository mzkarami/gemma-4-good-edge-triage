## Objective
Improve latency-outlier guard reliability by ensuring same-hash historical latency windows are not accidentally starved by unrelated tail rows from other state hashes.

## Problem Found
`load_recent_keep_latencies_for_state_hash(...)` previously applied `lookback` as a global tail slice of `results.tsv` before filtering by `state_hash`.

Impact:
- In mixed-history ledgers, recent runs from other hashes could displace valid same-hash history.
- This could suppress outlier detection (`detect_latency_outlier_for_state_hash`) by dropping below `LATENCY_OUTLIER_MIN_SAMPLES` even when enough same-hash comparable keeps existed.

## Change Implemented
File: `triage_sandbox.py`
- Updated `load_recent_keep_latencies_for_state_hash(...)` to:
  - scan rows in reverse chronological order,
  - collect only matching same-hash comparable `keep` latencies,
  - stop when per-hash `lookback` count is reached,
  - reverse collected values before returning so output stays chronological.

This preserves intended semantics: `lookback` now applies to recent comparable runs of the same state hash, not to unrelated global rows.
