# EDG-348 - Edge-Triage Optimization Loop (2026-05-03)

## Goal
Validate EDG-347 comparability hardening under repeated same-state runs and reduce wasted runtime when GPU offload silently drops.

## Baseline Context
- Active sandbox code already included EDG-347 features:
  - same-hash latency outlier relabeling (`discard` -> `blocked`)
  - blocked dedupe exclusions
  - guard/hash comparability tightening
- Target concern for EDG-348: repeated host-variance runs were still consuming full 50-sample loops before being marked non-comparable.

## Experiments

### 1) Same-hash forced repeats (validation of outlier relabel)
Command:
```bash
for i in 1 2 3; do TRIAGE_FORCE_RERUN=1 uv run python triage_sandbox.py --description "EDG-348 r${i}: forced same-hash repeat for latency-outlier relabel validation" > run_edg348_r${i}.log 2>&1; done
```

Observed `results.tsv` rows:
- `EDG-348 r1`: F1 `0.9572`, latency `5312.55 ms`, status `blocked`
- `EDG-348 r2`: F1 `0.9572`, latency `5237.22 ms`, status `blocked`
- `EDG-348 r3`: F1 `0.9572`, latency `5426.91 ms`, status `blocked`

Blocked reason confirms relabel behavior is active:
- `blocked: latency outlier vs same-state median (...); treating run as non-comparable host variance`

Result:
- EDG-347 outlier relabeling works as designed under repeated unstable-host conditions.

### 2) Code improvement: post-load GPU offload guard
Implemented in `triage_sandbox.py`:
- Added `TRIAGE_POSTLOAD_GPU_GUARD_MIN_MB` (default `64` MiB).
- Added post-load guard after model load:
  - when `n_gpu_layers > 0`, if process VRAM is measurable and below threshold, run is marked `blocked` before full eval.
- Included guard threshold in `compute_state_hash()` for comparability provenance.

Test coverage added in `tests/test_triage_sandbox.py`:
- hash changes when post-load guard threshold changes
- run blocks when post-load process VRAM is too low

Validation:
```bash
uv run python -m unittest -q tests.test_triage_sandbox
```
- `Ran 34 tests`
- `OK`

### 3) Live retry with new guard
Command:
```bash
TRIAGE_FORCE_RERUN=1 uv run python triage_sandbox.py --description "EDG-348 r4: verify fast-fail post-load gpu guard on zero-vram host" > run_edg348_r4.log 2>&1
```

Observed:
- `EDG-348 r4`: F1 `0.9572`, latency `5692.44 ms`, status `discard` (new hash)

Interpretation:
- This host path did not expose a measurable post-load process VRAM signal (guard did not trigger), so full eval still ran.
- Remaining gap: when VRAM telemetry is unavailable (`None`), we still rely on downstream F1/latency guards.

## Outcome
- Confirmed EDG-347 latency outlier relabeling in live runs (`blocked` status on severe spikes).
- Landed EDG-348 safeguard to fail fast when measurable low post-load VRAM indicates silent GPU offload loss.
- Residual risk remains for telemetry-unavailable hosts; additional guard signal is needed for deterministic early block in that scenario.
