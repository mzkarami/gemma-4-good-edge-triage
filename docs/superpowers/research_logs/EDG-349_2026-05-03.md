# EDG-349 - Edge-Triage Optimization Loop (2026-05-03)

## Goal
Reduce wasted runtime on non-comparable host states where GPU layers are requested but runtime effectively falls back to CPU-like behavior with no usable GPU telemetry.

## Baseline Context
- EDG-348 added a post-load guard that blocks when process VRAM is measurable and below a threshold.
- Residual gap from EDG-348: when process VRAM telemetry is unavailable (`None`), full 50-sample runs could still execute and end as low-F1/high-latency discards.

## Experiments

### 1) Baseline forced rerun on current codepath
Command:
```bash
TRIAGE_FORCE_RERUN=1 uv run python triage_sandbox.py --description "EDG-349 r1: heartbeat baseline forced rerun on edg348 codepath" > run_edg349_r1.log 2>&1
```

Observed:
- `EDG-349 r1`: F1 `0.9572`, latency `6090.77 ms`, VRAM `0.00 GB`, status `discard`
- Runtime warnings/signals indicated CUDA initialization failure and no meaningful GPU telemetry.

Interpretation:
- Confirms remaining EDG-348 gap: non-comparable host path still consumed full benchmark runtime before discard.

### 2) Code change: telemetry-unavailable post-load guard
Updated `triage_sandbox.py` to add a second post-load fast-fail branch:
- Condition:
  - `selected_gpu_layers > 0`
  - `detect_process_vram_mb()` returns `None`
  - `torch.cuda.is_available()` is `False`
  - `TRIAGE_ALLOW_GUARDED_CPU_BENCHMARK=0`
- Action:
  - append `blocked` row with explicit non-comparable reason
  - cleanup and return before full evaluation
- Duplicate blocked-row suppression added via `has_blocked_reason_for_state_hash(...)` fragment check.

### 3) Test coverage
Added test:
- `test_run_triage_blocks_when_postload_gpu_telemetry_missing_and_cuda_inactive`

Adjusted existing mocked-success tests to set post-load process VRAM explicitly so they remain comparable under the new guard.

Validation:
```bash
uv run python -m unittest -q tests.test_triage_sandbox
```

### 5) Repeat stability check (dedupe + fast-fail)
Command:
```bash
for i in 3 4; do
  TRIAGE_FORCE_RERUN=1 uv run python triage_sandbox.py --description "EDG-349 r${i}: repeat fast-fail stability check" > run_edg349_r${i}.log 2>&1 || true
done
```

Observed in both logs:
- `Model loaded in ~1.0s (GPU Active: False)`
- `Duplicate post-load GPU telemetry blocked state for current hash; skipping duplicate results entry.`
- blocked reason remains `post-load GPU telemetry unavailable with CUDA runtime inactive...`

Result:
- Fast-fail remains stable across repeats.
- Duplicate suppression prevents `results.tsv` spam for identical blocked causes on the same state hash.

## Outcome
- EDG-349 closes the telemetry-unavailable gap left by EDG-348.
- Non-comparable GPU-intent runs now fast-fail deterministically, preserving hourly loop throughput and avoiding expensive discard-only evaluations.
